当前范围：JavaScript / TypeScript / HTML / CSS 四门浏览器原生，加上两门 WASM 语言 Lua 5.4 与 SQLite（SQL）。JS/TS 默认走 Worker（worker.terminate() 能真杀无限循环），HTML/CSS 走 sandbox="allow-scripts" 的 iframe，TypeScript 用官方 transpileModule 动态加载转译。

Lua 实现：wasmoon 1.16.0 跑在独立 module Worker 里，glue.wasm 用 Vite ?url 自托管（默认会去 unpkg，内网/离线不可用，已显式覆盖为同源地址）。Worker 先初始化引擎发 ready，主线程收到后才起墙钟计时 —— wasm 下载与实例化不算进用户代码预算；同步死循环靠 worker.terminate() 真杀。Lua 侧薄壳把 print/io.write 接到输出通道（绕开 Emscripten 行缓冲，无换行也不丢）、io.read 读契约注入的 stdin、os.exit 改成可读错误；第二个 .lua 文件挂到内存 FS，可用 dofile('/helper.lua') 加载。traceAllocations: true 让内存用量与上限都可计数，probes 里能读到 Lua 版本、wasm URL、实际内存用量。

SQL 实现：sql.js 1.16.0 / SQLite 3.54.1 同样跑在独立 module Worker，sql-wasm-browser.wasm 用 ?url 自托管并显式传 locateFile（glue 默认按 scriptDirectory 拼路径，在 module Worker 里不可靠）。不用 db.exec() —— 它会一次性把整个结果集物化进 JS 数组，输出限额根本挡不住内存；改用 iterateStatements + stmt.step() 逐行读，每 64 行批量回传，触到输出字节或行数上限立即停。同一次运行内多语句共享同一个 DB，第二个 .sql 文件作为初始化脚本先执行；NULL/BLOB 显式可读，中文不做全角宽度对齐。能力缺口如实登记：sql.js 没有 wasmoon 那样的 setMemoryMax，所以只有墙钟 + 输出字节 + 行数 + Worker 隔离四道闸，probes.memoryCapability 明写 no-allocator-cap，usage.memoryBytes 一律不填（不拿 0 冒充用量）。无限递归 CTE 靠 terminate() 真杀。

契约先行：RunRequest 已含 target: browser | server、limits（wall/cpu/memory/output）、files[]、stdin；RunResult 已含 exitCode: number | null（浏览器没有退出码，不假装 0）、usage、probes、preview。能力表 Capability 由注册表 active() 推导 —— 没接线就置灰，单测骗不过去。加一门语言只要登记 + 实现 Runner + 注册 + 加示例 + 补端到端判据，UI 一行不改。

迁移到服务端：src/runners/server/piston.ts 已实现 Runner 接口、buildPistonBody()（显式传内存限额，不吃 Piston 默认的 -1）与 mapPistonResponse()（RE/SG/TO/OL/EL/XX 六种状态映射），默认 enabled: false 且不注册。启用只需在 createRegistry() 传 ServerWiring，能力表会自动出现 server 位置与「可判分」。

已知边界：iframe 内同步死循环会冻结标签页（浏览器限制），该模式的超时判据不做自动验证；JS/TS 请用 Worker 载体。首版不支持模块 import/export。预览 iframe 是 opaque origin，event.origin === 'null' 证明不了任何事，代码里靠 event.source + requestId 双重校验。Lua 没有真实网络与文件 IO，每次运行新建引擎（变量不跨运行），没有 REPL session；SQL 是纯内存 DB，每次运行新建，不持久化到 IndexedDB，也没有真实文件/网络。构建时 Module "module" externalized 警告来自 wasmoon UMD 引用但浏览器下不用的 node 内建模块，dev 与 dist 两层真机都已验证。

验收：npm run verify（类型检查 + 49 条单测 + 构建）；npm run smoke 用本机 Chromium + CDP 打开 ?selftest=1 跑真浏览器端到端判据（59 条：57 绿 / 2 条按白名单记账跳过）；npm run smoke:preview 在 dist 产物里跑同一套判据，验证 build 后两套 wasm 的 /assets/ 路径仍能加载。七个拆线负例：单测层 npm run negative（摘 CSS）、negative:lua、negative:sql 各精确红 1 条；浏览器层 smoke:negative（掐 iframe 回传）红 12、smoke:negative:lua（掐 Lua stdout）红 8、smoke:negative:sql（掐 SQL 结果行回传）红 7、smoke:negative:sample（把默认示例写坏）红 1，全部按红 id 集合精确比对、通过数押相对关系 —— 加一门新语言不会让老负例误报。

判据的一条硬规矩：sample/* 六条判据直接跑 SAMPLES 原文，也就是用户打开页面点「运行」看到的第一份代码。v0.3 曾踩过：SQL 默认示例拿 SQLite 保留字 NOTHING 当列别名，自检里 51 条全绿却没一条跑过这份示例，用户一点就 near "nothing": syntax error。现在示例已改成 NULL AS "nothing"，并加了专门负例：把引号去掉必须精确红 sample/sql 一条。语言判据都用自检自己造的干净输入，天生抓不到「默认示例本身写错了」，这一层只能靠跑原文补上。

体积基线（1024 口径，gzip -9 实测）：与上一版 dd256cd 用同一脚本真实对照 —— 首屏 JS 10.85 → 11.79 KB，CSS 恒 1.58 KB，首屏合计 12.43 → 13.36 KB（+0.93 KB）。SQL 全懒加载：切到 SQL 编辑器下载语法包 5.88 KB；首次运行再下 sql-worker 16.13 KB + sql-wasm-browser.wasm 328.46 KB = 344.59 KB gzip，不运行 SQL 的用户一个字节都不下载。手册第五章的 sql.js 体积已按本轮构建产物实测订正（原先「约 1 MB / 400 KB gzip」是按包内多套构建估的量级）。后续每加一门语言继续按这个口径先量再合并。
