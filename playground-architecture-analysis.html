一、三种体积口径（最容易算错的地方）

网上「Pyodide 200MB」「DuckDB 142MB」「WebContainer 0.17MB」这类互相矛盾的数字，几乎全是口径混用。做预算前必须先把三者分开：

① npm 解包体积unpackedSize包装进 node_modules 的字节数。含多平台构建、测试、source map、示例，通常远大于实际下载量。
② 首次 HTTP 传输gzip / brotli用户第一次点这门语言真正下载的字节。wasm 压缩率高（约 2.6:1），已经是 zip 的标准库压不动。预算按这个算。
③ 常驻 / 峰值内存RSS运行时实例化后的线性内存 + JS 堆。WASM 编译期峰值另算，可比常驻高一个数量级。
三个典型反例（都实测过）
  • @webcontainer/api 解包仅 0.17 MB，但那只是 JS SDK；真正的 Node 运行时从 CDN 首次拉约 20 MB。
  • @duckdb/duckdb-wasm 解包 142.46 MB（内含 mvp / eh 两套各约 35–40 MB 的 wasm），浏览器按能力只加载其中一套，实际约 2.8 MB gzip。
  • pyodide npm 包解包 13.24 MB，官方 full 发行包 200+ MB（含全部预编译 wheel），而最小 core 首次传输实测约 6.44 MB。
另：1024 与 1000 口径差 2.4%，跨来源对比前先统一。本文一律 1024（MB = 1 048 576 B）。

二、推荐架构：统一契约 + 三层后端

一个 playground 其实是「一个编译器 + 一个沙箱，外面套了个编辑器」。编辑器是最便宜的一层，真正的设计在下面这层契约：

type Cap = 'stdin' | 'stdoutStream' | 'stderrStream' | 'exitCode' | 'interrupt'
         | 'packages' | 'files' | 'network' | 'threads' | 'graphics'
         | 'persist' | 'multiFile' | 'offline' | 'trustedGrading';

interface Runner {
  id: string;                      // 'browser-wasm' | 'browser-native' | 'remote-piston'
  lang: string;
  caps: Record<Cap, 'native' | 'emulated' | 'unsupported'>;   // 能力表：单一真值
  supports(c: Cap): boolean;        // UI 渲染前必过这一关
  run(req: RunRequest): AsyncIterable<RunChunk>;               // 流式输出
  abort(): void;                    // 必须能杀掉，不允许"未知"
}

type RunRequest = { language: string; files: File[]; stdin: string;
                    args: string[]; timeoutMs: number };
type RunChunk   = { stream: 'stdout' | 'stderr' | 'status'; text: string };
type RunResult  = { stdout: string; stderr: string; exitCode: number | null;
                    durationMs: number; timedOut: boolean; backend: string };

能力表是地基，不是文档。三档语义：native 真支持 / emulated 能跑但语义有偏差（必须给用户看提示）/ unsupported 置灰且写明理由。UI 的「安装依赖」「上传文件」「启用网络」「停止」按钮全部由 supports() 驱动，不许在组件里写 if (lang === 'python')。这套做法和你 kite 项目里的 56 个 CapFlag 是同一个道理，只是这里的能力缺口更硬——浏览器里缺的是 OS，不是产品决策。

B2 浏览器 WASM 编译链C / C++ / GoWASI shim + 内存 FS，编译产物再用 WASM 跑约 23 MB 压缩 / 100 MB 解包编译慢、常驻几百 MB；异常/线程/std 子集语义有偏差

7. Rust / C# / 其它 B3

  • Rust：rustc 依赖 LLVM，塞进浏览器不实用（rubrc 是 WIP 实验，要 COOP/COEP，不支持外部 crate / proc macro）；只做前端类型检查的 rust-js 预估 21–32 MB brotli 且不生码。官方 Rust Playground 本身就是服务端容器。结论：走 B3。
  • C#：Blazor WASM 是把 .NET 运行时（约 1.3–2.5 MB 压缩）+ 预编译 DLL 下载到浏览器执行，不是源码编译器；Roslyn 编译到 WASM 无成熟方案。要「输入 C# 源码点运行」，走 B3。
  • Kotlin / Scala / Swift / Dart / Julia / Perl / Bash / Fortran / Haskell / 汇编：浏览器端没有可用的源码级运行时，一律 B3。Bash 尤其别被 WebContainers 的虚拟 shell 迷惑，那不是真 bash。

口径订正：这三者不是同一档，不能并列叫「服务端沙箱」。Piston 与 Judge0 的隔离基础是同一个东西（isolate，进程级）；Firecracker 是 VM 级；gVisor 居中。而且反直觉的一点：为了创建 namespace / cgroup / chroot，Piston 与 Judge0 自身都必须运行在特权容器里 —— 真正的边界不在 isolate，而在「执行节点是否与你的业务、数据库、凭据同机」。把 Piston 塞进主站同一台机器，等于把整机暴露给任意用户代码。
最小可行安全形态：独立执行节点 + 无云凭据 / 无内网可达 + 默认禁网 + 每任务显式限额 + 外层再套 gVisor 或 microVM（或直接把 L1 整个装进 L3）。

七、部署与安全硬约束

  1. 独立可注册域，不是子域。主站若是 playground.example.com，预览必须用与主站不同的可注册域（如 cdpn.io 对 codepen.io），而不是 run.example.com 这种同站子域。同站子域挡不住 Domain=example.com 的 cookie，密码管理器也可能把登录填进预览页的表单。
  2. sandbox="allow-scripts"，绝不能同时给 allow-same-origin（同源 frame 能自己摘掉 sandbox 再重载）。frame 处于 opaque origin，event.origin 是 "null" 证明不了任何事 ⇒ 每条消息都要校 event.source === iframe.contentWindow。
  3. CSP：runner 页 default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval' blob:，禁止加载外部脚本和外联数据。postMessage 是 structured clone，函数 / DOM 节点 / 循环引用都过不去，输出序列化要限深度并用字符串标签替代。
  4. 无限循环只能外部杀。同步循环不 yield，同线程的 setTimeout 永远轮不到，try/catch 也接不住。看门狗在宿主，超时 worker.terminate() + 重建；iframe 路线只能销毁重建。Pyodide 想做「优雅中断」需 setInterruptBuffer() + SharedArrayBuffer。
  5. COOP/COEP 是全局开关。Cross-Origin-Opener-Policy: same-origin + Cross-Origin-Embedder-Policy: require-corp 一开，所有第三方资源都要 CORP/CORS 头，图片、字体、CDN、嵌入 iframe 可能成片失效。建议把需要 SharedArrayBuffer 的运行时放在单独子站，主站保持普通，避免全站改造；代价是跨域通信与部署复杂度。HTTPS 是硬要求（localhost 例外）。
  6. 版本一致性。「JS 胶水在 npm 包里、.wasm 产物在 CDN」是常见形态（Pyodide / DuckDB / webR / esbuild 都是）。两侧版本必须严格 pin 同一个常量，错版直接运行时崩。所有资源 URL 做成运行时可配置，别硬编码进 bundle —— 内网/离线交付就靠这个。
  7. 缓存策略。运行时资源 Cache-Control: public, max-age=0 + ETag（二次访问实测约 2 KB）；Service Worker 预缓存；按语言懒加载，选中才下载；产物闸门禁止运行时进首屏 chunk。
  8. 授权审查（会直接否决方案）：WebContainer API 的 npm 包是 MIT，但运行时是专有的，商用生产需授权，开源用途免费；CheerpJ 社区版不可自托管、需署名；webR 继承 R 的 GPL-2.0-or-later，闭源商业分发要么合规开源要么改走服务端 R。

八、落地顺序与验收判据

  1. 先写契约和能力表，并给它们写测试。先把 RunRequest/RunResult、能力三档、supports() 定死，再动任何运行时。这一步最便宜，返工最贵。
  2. 打通 B0 + B3 最小闭环：JS 走 iframe，Python 走 Piston。把编辑器、输出面板、stdin、超时、分享链接、错误展示全部做完。此时「多语言」已经是真的，且没有体积风险。
  3. 按体积从轻到重逐个迁到 B1：Lua(0.44) → SQL(3) → Python(6.4) → PHP/Ruby(20–30) → R(30，注意 GPL)。每接一门都补端到端冒烟 + 拆线负例。
  4. B2 编译链最后做（成本最高、收益最窄），除非明确要 C/Go 教学。优先复用 YoWASP / Go 官方工具链的现成 WASM 构建，不要自己编 LLVM。
  5. 最后做部署层：CDN 镜像与运行时 URL 可配置、Service Worker 缓存、COOP/COEP 子域隔离、体积与缓存命中率监控。
验收判据（押「可观察副作用 + 可计数的量」，别押「没抛错」）
  • 每门语言固定 6 条端到端冒烟：stdout 回显、stderr + 非零退出码、stdin 回读、中文/UTF-8、无限循环被超时杀死且有明确 timedOut、依赖导入后能读回结果字节。
  • 拆线负例：故意把某门语言的 loader URL 改坏 ⇒ 只有这门语言精确红，其它语言全绿。这能抓住「运行时加载出来但根本没接线」——单测对没接线天生免疫。
  • 缓存判据：二次访问运行时请求 0 body（看 transferSize），不是「感觉变快了」。
  • 产物闸门：首屏 ≤ 1 MB，运行时资产不在首屏 chunk；改回静态 import 必须精确红。
  • 能力置灰判据：声明 unsupported 的按钮真的点不动，且给出可读理由。

九、坑清单

  1. 「支持多语言」的成本是线性叠加的，不是一次性投入。五种语言全部预加载就是 40–60 MB 首屏，移动网络不可用。单语言 ≤ 5 MB + 懒加载应写成硬预算指标。
  2. 「包能加载」≠「能跑用户代码」。运行时初始化成功、单测全绿，都可能只是 loader 通了；只有端到端跑一段真代码才作数。
  3. 体积数字按版本核对。Pyodide 从 0.2x 的 6.4 MB / 4–5 s，到 314.x 的 CPython 3.14.2；PHP.wasm 2026-03 靠 MAIN_MODULE=2 单次砍掉 122 MB。旧博客结论不能直接引用。
  4. 「未做」清单本身会漂移。开工前先 grep 代码，别拿一份凭印象维护的能力表当真值。
  5. 语义偏差要显式标注，不能静默。wasm32 指针 4 字节、NULL 读不崩、C++ 异常、Go 的 poll_oneoff、Python 无 threading/socket —— 这些不是 bug，是能力边界。
  6. 用户以为的「超时」可能是「编译」。编译时间和执行时间必须分开计时、分开限时，否则 C++ 第一次点运行必然被误杀。
  7. Piston 的两个默认值都要改，内存比 stdout 更危险。stdout 默认截断 1024 字符，yes 类程序或大表格会静默丢输出（状态 OL / EL）；而 run_memory_limit / compile_memory_limit 官方默认是 -1，即不限制内存 —— 一段 [0]*10**9 就能把执行节点打 OOM。接入第一件事是显式传内存上限与输出上限，并把 TO / SG / RE / OL / EL / XX 六种状态映射到 UI。
  8. CDN 版本与 npm 版本错配是最难查的一类线上崩溃，因为它只在特定浏览器/缓存状态下出现。
  9. 不要在移动端常驻多个 WASM 运行时。WASM 编译期峰值 1–4 GB，直接 OOM；切语言先 terminate。
  10. 客户端结果不可信。凡涉及判分/评测，浏览器端只能当「预览」，真值必须服务端再跑一遍。
  11. 全站 COOP/COEP 之前先盘点第三方资源。这是部署层最容易被低估的一次性改造成本。
  12. 授权要在选型阶段过一遍：WebContainer / CheerpJ / webR 三家各有硬约束，等做完再发现就得推翻架构。
  13. 「零外联」必须抓包，且抓包器自己要有证据。只在 page session 上 Network.enable 收不到 module Worker 的请求，此时「外部请求 0 条」是空证据而不是零外联；要 autoAttach worker target 逐个 enable，并确认真的抓到了本地资产请求（本轮要求 ≥3 条 /pyodide/），否则判失败。
  14. core 与 full 分发不是一回事。Pyodide npm 的 core 分发不带 wheel、没有 micropip；loadPackagesFromImports() 会外联并卡 25 s 以上，loadPackage() 在 core 下静默失败。首版只能明令禁止自动装包，并把缺失包错误翻译成人话。
  15. 引擎复用 ≠ 进程隔离。复用 Worker 能省掉 9.6 MB wasm 的重复 boot，但 sys.modules 会跨运行残留；靠每次新建 globals 只能隔离变量。超时 / 取消必须 terminate() 并清空缓存，否则下一次会复用一个半死的引擎。

十一、专题：能否只留「A 原生 + 服务端」，把 B/C 全砍掉

结论：能，而且对「输入源码 → 输出文本」这一类 playground，这是更省事、覆盖更全、结果更可信的默认方案。但 A 不能砍。 B（WASM 解释器 / 运行时）和 C（浏览器内编译链）可以从「必做」降级为「可选加速 / 离线降级」；A 的性质则要从「执行后端之一」改成「浏览器环境本身」——DOM、Canvas、CSS 预览、交互事件没有服务端等价物。真正要改的不是删掉几层，而是把「执行位置」抽象进 Runner 契约。

11.2 唯一不能服务端化的边界：浏览器语义

服务端能跑「语言」，跑不了「浏览器」。Node 与浏览器是同一门语法、两套 API，这一条决定了 A 的存留，跟语言覆盖率无关。

所以精确的答案是：如果产品定义是「算法练习 / 后端语言试跑 / 文档代码可运行」，A 可以退化成纯编辑器，B/C 全砍，S 覆盖全部语言。如果产品定义含「前端 playground」，A 是产品语义的一部分，砍了就不是同一个产品了。

11.3 砍掉 B/C 后，服务端覆盖能力严格更强

Piston 官方列表约 88 个运行时，Rust / C# / Kotlin / Swift / Bash / Go / Zig / Haskell / Java / PHP / Ruby / R / Lua / SQLite 全都在，而且是原生编译器 / 解释器，不是 WASM 移植版。一次性消掉的能力缺口包括：

11.5 三档隔离：Piston / Judge0 与 Firecracker 根本不是一档

原第四章把三者并列叫「服务端沙箱」是模糊口径，已按 2026-11-11 官方 README 订正（见第四章第 8 节表格）。关键是反直觉的一点：为了创建 namespace / cgroup / chroot，Piston 与 Judge0 自身都要求 --privileged 容器；Judge0 官方 compose 的 server / worker 都是 privileged: true，运行用户还带 NOPASSWD: ALL。所以真正的边界不在 isolate，而在执行节点是否与业务、数据库、云凭据同机。

  • L1 进程级：Piston / Judge0 = isolate（namespace + chroot + cgroup + 非特权用户），共享宿主内核。适合内网可信用户、教学；不适合裸奔公网的完全不可信代码。
  • L2 用户态内核：gVisor，syscall 由 Go Sentry 接管，宿主内核不直接暴露；无需 KVM，容器级启动，IO 密集有 syscall 税。适合套在 L1 外面做第二层。
  • L3 硬件虚拟化：Firecracker / Kata，KVM + 独立 guest kernel + jailer。官方数字：用户态启动 <125 ms、每 VM 开销 <5 MiB、单宿主 150 VM/s、Apache-2.0。多租户 / 公开 SaaS / 跑 AI 生成代码时优先，代价是要 /dev/kvm、自管 rootfs 与快照池。
最小可行安全形态：独立执行节点 + 无云凭据 / 无内网可达 + 默认禁网 + 每任务显式限额 + 外层再套 gVisor 或 microVM。把 Piston 塞进主站同一台机器，等于把整机交给任意用户代码。

11.7 成本账（给公式，数字是估算不是实测）

峰值 vCPU ≈ (日运行次数 × 平均 CPU 秒) / (峰值集中小时 × 3600 × 目标利用率)
峰值内存 ≈ 并发上限 × 单任务内存上限 + 基础服务（Judge0 四容器约 200 MB 起）

例（假设，需自行压测替换）：1 万 DAU × 5 次/日 × 0.5 CPU·s
  = 2.5 万 CPU·s/日 ≈ 7 CPU·h/日
  若 30% 集中在 2 小时、按 60% 利用率 ⇒ 约 1.6 vCPU 常驻 + 队列余量
  并发 20 × 256 MB = 5 GB + 基础服务 + 执行节点隔离冗余

WASM 路线的对应成本是 CDN 出流量（一次性、可缓存）+ 用户设备 CPU/内存；DAU 越大、单次越轻，WASM 越接近免费，服务端越按次付钱。反过来，DAU 小、单次重（编译 Rust、跑数据分析），服务端反而更划算，因为用户设备根本扛不住。

11.9 推荐骨架：把「位置」写进契约，而不是写死在 UI

interface RunRequest {
  language: LangId;
  files: { name: string; content: string }[];
  stdin?: string;
  limits: { cpuMs: number; wallMs: number; memoryBytes: number; outputBytes: number }; // 显式传，别吃默认值
}
type ExecTarget = 'browser' | 'server';
interface Capability {
  lang: LangId;
  targets: ExecTarget[];      // browserOnly / serverOnly / both
  prefer: ExecTarget;         // 默认路由，可随在线状态切换
  offline: boolean;
  trusted: boolean;           // 结果能否用于判分
  nativeApis: string[];       // 只有 browser 才有的语义，用于置灰理由
  reason?: string;
}
  • UI 只问 supports() 与 prefer，路由层决定本地还是远端；将来想加回 Pyodide 做离线降级，不动一行 UI —— 这与 kite 的 56 个 CapFlag 三档是同一套思路。
  • 默认全部走 S，A 只处理 browserOnly 的语言；B/C 只在出现明确离线需求或 CDN 账单压力时按需引入。
  • 断线时 prefer 自动切到 browser（若该语言 offline 为真），否则给出可读降级，不要白屏。
  • 能力表真值来自 GET /api/v2/runtimes 的 language + version 动态生成，不要手写常量——否则服务端装了新语言，前端永远看不见。

11.10 纯服务端路线的验收判据

  • 内存负例：提交吃满内存的程序，执行节点存活、返回明确限额状态，不是整节点 OOM。这条最能区分「配了」和「以为配了」。
  • 六种状态映射：RE / SG / TO / OL / EL / XX 各有对应的 UI 文案；超时与输出超限不是「运行失败」一句话带过。
  • 拆线负例：把某语言的服务端包路径改坏 ⇒ 只有该语言精确红，其它语言全绿；这抓的是「能力表写了但没接线」。
  • 逃逸负例：读 /proc/1、探测内网地址、写宿主挂载、起 300 个进程，全部被拒且落审计日志。
  • 降级判据：断网 / 执行服务 5xx / 排队超时，UI 有可读提示且可重试，不是白屏或永久转圈。
  • 判分真值：判分只读服务端结果；同一份代码浏览器预览与服务端结果不一致时要显式提示，不要静默取其一。

最后一句判断：纯服务端不是「少写代码」，而是把复杂度从前端体积与浏览器兼容性，换成一台要长期有人维护的隔离执行节点。团队里若没有人愿意持续跟 CVE、管镜像、看队列，WASM 反而更省；若本来就有后端和机器，A + S 是明显更稳的起点。

十二、落地实测：三门 WASM 的真实接线账（v0.2 ~ v0.4）

2026-11-12 追加。前十一章是选型分析，本章只记代码真正跑起来之后才看得见的事实：体积一律来自本仓库构建产物（1024 口径，gzip -9；下表把历史上的「KB」统一记作 KiB），不是 registry 元数据，也不是公开 ADR。

12.1 逐门增量：首屏几乎不动，钱在第一次点运行时付

版本首屏 JS + CSS新增语言首次运行下载形状

12.2 自托管不是一种写法，是三种

  1. 单文件 + 显式 URL（Lua）：wasmoon 默认去 unpkg 取 glue；改成 Vite ?url 引入并把绝对 URL 传进引擎。dev 是 /node_modules/、dist 是 /assets/<hash>.wasm，两层都要真机验。
  2. glue 自己拼路径（SQL）：sql.js 按 scriptDirectory 拼 wasm 名，在 module Worker 里不可靠；必须显式给 locateFile。
  3. 整套固定文件名目录（Python）：loadPyodide() 按 indexURL 拼四个固定名字，而 Vite 会把 pyodide.mjs 打进带 hash 的 chunk。解法是 scripts/sync-pyodide.mjs 在 postinstall / dev / build 三处幂等同步 public/pyodide/（运行时产物不入库、版本精确 pin、manifest 记字节数），Worker 显式传同源 indexURL。

共同纪律：不让运行时自己猜 URL；probes 里如实记 URL 只算自述，真机 CDP 抓包才算证据（见第九章第 13 条）。

12.3 每加一门语言的固定五步与判据纪律

  1. 登记 LangId / LANG_DEFS / SAMPLES → 实现 Runner → createRegistry() 注册 → CodeMirror 语法包动态 import → 补端到端判据 + 拆线负例。UI 一行不改，能力表由注册表 active() 推导。
  2. 拆线负例押红 id 集合 + 相对通过数：押绝对通过数，加一门语言老负例必然误报；本轮九个负例（4 单测 + 5 真机）全部精确。
  3. sample/* 跑 SAMPLES 原文：v0.3 的 51 条全绿没一条跑过用户打开页面第一个点的代码，SQL 默认示例用保留字 NOTHING 当别名，一点就语法错。判据押 status / 无 error 诊断，不押输出字节，免得与 stdout 负例耦合。
  4. 两阶段计时：引擎 ready 之后才起墙钟，wasm 下载与实例化不算进用户代码预算；同步死循环只能靠 worker.terminate() 真杀。
  5. 能力缺口如实登记：sql.js 无 allocator 上限 ⇒ no-allocator-cap 且不填 usage.memoryBytes；Pyodide core 无 wheel ⇒ stdlib-only 且禁用自动装包。不拿 0 冒充用量，不把「档位」写成「已实现」。

12.4 三个只在实现阶段才暴露的坑

  • Node 侧探测不能当浏览器结论：file:// 的 indexURL 在 Node 里能勉强走通，浏览器必须 HTTP 同源；反过来 loadPackagesFromImports() 的超时也无法用 Node 复现。
  • API 名称看着对，语义可能正好相反：SQL 用 db.exec() 会把整个结果集物化进 JS 数组，输出限额等于没设；改逐行 step() 才让限额真正生效。无限递归 CTE 若每行都回传，会先触输出限额而不是超时，超时判据得改用聚合语句。
  • 单元判据对「没接线」天生免疫：能力表若手写常量，Runner 没注册时单测一样全绿；只有 registry 接线真值 + 拆线负例抓得住。

十三、决策分叉：A′ 非 Docker 路线 vs 官方 Docker 推荐（v0.5）

这一章专门写给「时间长了以后忘了为什么」的自己
官方 Piston 的推荐部署是 docker run --privileged + 纯 cgroup v2 + Linux。 本项目 v0.5 刻意不这么做，改用 Go 单二进制的本地进程执行节点（A′）。 这不是「先凑合、以后再改」，而是威胁模型不同：团队内几个人验证自己写的可信片段， 不需要内核级隔离。但只要出现「对公网开放 / 跑不可信代码 / 结果用于判分」任一条， 必须回切官方方案，不能靠给 A′ 加个 token 就把它当沙箱用。

13.1 官方真值（2026-11-12 按一手来源核对，别信二手博客）

  • 官方 readme.md 的 Host System Package Dependencies 明写 Docker / Docker Compose / Node ≥15 / cgroup v2 开启且 v1 关闭；「Just Piston (no CLI)」也要 Docker，命令是 docker run --privileged ... ghcr.io/engineer-man/piston；docker-compose.yaml 里 privileged: true。
  • 原理原文：Piston uses Isolate inside Docker，隔离靠 Linux namespaces / chroot / 多个非特权 uid / cgroup。api/src/docker-entrypoint.sh 会直接 mkdir /sys/fs/cgroup/isolate、写 cgroup.procs 与 cgroup.subtree_control，并显式拒绝 v1+v2 混合模式 —— 这就是它必须特权、必须 Linux 的原因。
  • 脱离 Docker：官方不支持。Node API 是纯 JS、isolate 只是 make install 一个二进制，裸机理论可跑，但上面那段 cgroup 初始化在 systemd 主机会抢 cgroup 所有权，得改成 delegate，等于维护一份 fork。跨平台：Linux 原生 ✓；Windows / macOS 只能借 Docker Desktop / WSL2 的 Linux VM 间接跑；Windows 原生 ✗（内核原语不存在）。
  • 搜索引擎里有中文文章写「Piston 无 Docker 依赖、内核级沙箱」，与官方 README 直接冲突。裁判是官方条文，不是博客。
  • 公共 API 自 2026-02-15 起不再免费发 key，且明确不给个人项目 ⇒ 只能自建。

另加了 src/runners/server/protocol.ts 作为 Piston v2 线协议的唯一真值：buildExecuteBody()（限额显式传，不吃对方默认 -1）、mapExecuteResponse()（RE/SG/TO/OL/EL/XX 六码映射）、emitServerResult()。A′ 节点按 Piston v2 兼容子集实现 /api/v2/runtimes + /api/v2/execute，于是 Go 优先接入的同时把「server 通路」真跑通了，而不是只留一个 enabled:false 的骨架。

13.6 Ruby / PHP / R / Java 走服务端后的授权口径

切到服务端后授权压力变小而非变大：WASM 路线要把运行时二进制分发到每个浏览器才触发 GPL / 专有条款，服务端只在自己机器上装。但 R 本体是 GPL-2|GPL-3，CRAN 里有 AGPL-3 包（对外服务触发 §13）；OpenJDK 是 GPLv2+CPE，Oracle JDK 是 NFTC（免费窗口带日历，JDK 21 自 2026-10 CPU 起转 OTN）；PHP 8.5 及更早是 PHP License 3.01（第 3/4 条名称限制、第 6 条强制署名），新版已改 BSD-3-Clause；Ruby / Go 是宽松许可。装包前确认发行版与版本，别把第三方预编译 tar 直接对外分发。这不是法律意见，对外服务前请法务过一遍。

13.8 v0.6：从单语言节点到「规格表 + 动态探测 + 可配置路径」

接 PHP 时何工提了个很实际的要求：有些运行时是便携式的，不在 PATH、也没写注册表，得能在后端指到绝对路径；网页前台不用暴露这个选项。于是这一轮没有再写第二个 if language == ... 分支，而是把节点整体泛化：

  • GET /api/v2/runtimes 每次真探测：不缓存、不硬编码版本；disabled 优先（「关」必须是第一句），path 配了就 os.Stat 校验，否则 exec.LookPath 回退；再带 3 秒超时跑版本命令。探测失败的语言不登记 ⇒ 前端把「必须预装工具链」从隐含前置变成可见约束（unavailable + 安装/配置指引）；POST execute 也重探测一次，便携盘拔走后不会拿旧路径跑。/health.missing 给原因，不污染线协议。
  • 路径配置只在后端：servers/local/runtimes.json 是入库模板，runtimes.local.json 是本机覆盖且不入库；-config 可显式指定，文件不存在直接报错。相对路径在加载时转绝对（执行阶段 cmd.Dir 是临时目录）。source = config | path 随 runtimes 与 probes.runtimePathSource 如实回报。

三个新坑（都会伪装成全绿）：

  1. ★★ go build -o 与 run 必须用同一个 exeName：抽 spec 表时把 Windows .exe 后缀挪进 run plan，compile 仍写无后缀名 ⇒ 编译 code=0 却报 program.exe: file not found。手工 API 验证抓到，纯函数单测抓不到。现在后缀在 execute() 统一补一次。
  2. ★★ CDP 抓包证明不了节点进程的网络行为：浏览器只监听自己的 target，节点进程发的请求一条也看不到。「零外联」判据只证明前端资产同源自托管；服务端侧只能靠 probes.network 自述 + 行为判据，都不能替代内核隔离。PHP 关掉 URL 包装器只是尽力而为，curl / sockets 仍在。
  3. ★ 配置路径生效不能靠文档自述：新增 npm run check:node，在独立端口重启节点四次，只押接口看得见的事实 —— 配了 path ⇒ source=config 且真吐字节；坏路径 ⇒ 从 runtimes 消失 + execute 400；disabled:true ⇒ PATH 里有也不登记；path:"" ⇒ source=path。共 14 条。

13.9 v0.7：用 Cygwin Perl 提前验证「非原生 Windows 运行时」这条接缝

何工这一门刻意不选 ActivePerl / Strawberry Perl，而指定 Cygwin Perl（D:\cygwin64\bin\perl.exe，5.32.1，不在 PATH、没写注册表）。目的不是加语言本身，而是把「本项目调用 Cygwin / MSYS2 / WSL 这类非原生 POSIX 运行时是否符合预期」提前试出来 —— 用他的话说「即便出问题也在预期之中，坑要记下来」。结论：跑通，没有阻断性问题，但确认了一组与 WASM 时代完全不同的坑类型。

  • 手动配置路径从「可选功能」升级成「唯一接法」：v0.6 加 path 覆盖时，PHP 其实仍在 PATH 里，算不上真用例。这次 check:node 的 fallback/perl-follows-path-truth 给出反证：清空 path 后 PATH 里没有 perl ⇒ 该语言立刻从 runtimes 消失、能力表置灰，证明它完全靠配置，不是碰巧被 LookPath 找到。
  • 宿主风味必须探测，不能硬编码：detectArgs 一次输出 $^V|$^O（v5.32.1|cygwin），flavorRe 解析后写进 runtimes[].flavor 与 probes.runtimeFlavor。判据 perl/flavor 让解释器再自报一次与节点回报核对，不押死 cygwin；同一条 spec 换挂 Strawberry（MSWin32）或 Linux perl，代码一行不改。
  • 「阉割」换了类型但没消失，还多了一层 POSIX 视图差异：WASM 阉割语言能力（第三方包 / 网络），A′ 阉割运行环境（无内核隔离、临时目录每次销毁），Cygwin 再叠加 /cygdrive/ 路径、/ 分隔符、$^O=cygwin、DLL 靠 exe 同目录、. 不在 @INC。Windows 三种路径写法作为 argv 参数它都认，但代码里硬编码 C:\ 做 open 仍会踩坑。
  • 语言能力变强 ≠ 隔离档变高：Cygwin Perl 有完整 socket / system() / fork()，比 Pyodide 强得多，但 A′ 没有笼子 ⇒ 仍是 process-only / advisory、结果不可判分；probes.network=no-enforcement;IO::Socket-available 如实登记，别对外说「零外联」。

四条最贵的坑（完整 10 条、15 项实测表与可复用检查清单在 servers/local/README.md §8）：

  1. ★★ 中文 argv 假象：Git Bash（MSYS2）把中文命令行参数按 cp936 传给 Cygwin 程序，perl -e 'print "中文"' 会 exit=0 且 stdout/stderr 全空，极易误判「Cygwin 不支持中文」。项目里代码走 files[].content 写 UTF-8 文件、不经 argv，完全正常 ⇒ 测非原生运行时一律走文件 + HTTP body，别用 shell 传中文 argv。
  2. ★★ UTF-8 编码层陷阱：只写 binmode(STDOUT, ':utf8') 而不 use utf8，UTF-8 字节被当 Latin-1 升级 ⇒ 乱码。正确是 use utf8; binmode(..., ':encoding(UTF-8)')。判据 perl/utf8-layer-trap 把这条钉死。
  3. ★ 宿主 PATH 没有 cygwin64，backtick 却照样能起 /bin/sh：Cygwin 运行时初始化自补 /usr/bin，cygwin1.dll / cygperl5_32.dll 靠 exe 同目录被找到（Windows DLL 搜索顺序）。节点不需要注入 PATH，但这是隐式环境，别当成「节点提供了完整 POSIX」；只拷 perl.exe 不带 dll 必然起不来。
  4. ★ Perl 5.26+ 把 . 移出 @INC：多文件 require 'helper.pl' 会挂，spec 加 -I . 才与 Go/PHP 语义一致；probes.includePath=-I. 如实登记。

对后续接 Ruby / R / Java / WSL 运行时的口径：① 路径用配置、能力表照这一刻探测；② 风味与版本由解释器自报，判据不押死具体值；③ 九项必验（stdin / stdout / stderr / 退出码 / 编码层 / cwd / 换行 / 子进程 / socket）；④ 越完整的运行时越不能对外宣称沙箱。分叉依据仍是 13.2 / 13.4 的威胁模型。

13.10 v0.8：Cygwin R 把「入口形态」逼成一等配置

何工这一门事先点明「R 解释器入口本质是 Bash 脚本，而不是可执行文件，会不会冒出意料之外的问题仍是未知数，值得一试」。结果确实出了三个意外，而且都不在纯函数单测的视野里：D:\cygwin64\bin\r 是 8953 B 的 #!/bin/sh wrapper，Windows 直接 exec 报 WinError 193；换 sh.exe 包装后继承宿主环境又 rc=127 且 stdout/stderr 全空；换成干净环境跑通了，R 的 stderr 里却混进宿主安全删除守卫的报错。结论：跑通了，但靠的是通用包装 + 环境净化，不是把 path 指过去就能用。

  • 通用化，而不是给 R 开后门：节点加的是 launcher / execPlan.wrap 与 spec 上两个可选钩子 wrapEntry(tool)（同目录 sh.exe <script>）、envFromTool(tool)（重建 PATH / HOME / CYGWIN）。execute() 仍然零语言分支，v0.6 的 builtinSpecs() 规格表只是多了两个字段。以后接 WSL 解释器、绿色 JDK 的 .cmd launcher、venv 里的包装脚本，都是同一套机制。
  • 探测与执行必须共用同一套启动计划：resolveRuntime() 跑 --version 时也要包装 + 用同一份环境，否则会出现「GET /api/v2/runtimes 能报出 r、点运行却 127」这种最难查的假绿。这是「判据绿了只说明我押的那条路是通的」在节点层的又一次应验。
  • 宿主环境是隐藏输入：宿主导出的 BASH_FUNC_RM%% / RMDIR%% / UNLINK%% 会在 Cygwin sh 启动时被 import，覆盖 rm；R 启动脚本一调 rm 就命中 MSYS2 版 CRLF 脚本，报 $'\r': command not found / set: pipefail: invalid option name。只剥 BASH_ENV 仍复现，最终要无条件剥 BASH_FUNC_ 前缀，并把变量名按 ToUpper 归一化（Windows 的 Path/PATH/path 大小写不敏感，按字面剥会漏）。
  • 能力缺口不许用开关盖掉：本机 stats.dll 缺 cyglapack-0.dll，R 每次启动都告警 stats 不在默认包里。设 R_DEFAULT_PACKAGES=base 能让 stderr 变干净，但 requireNamespace("stats") 仍是 FALSE、sd()/lm() 不可用 ⇒ 那是把宿主缺陷藏起来，不做。probes.startupWarning 如实登记，判据押「解释器自报 + 不可用时必须有告警」，换机器修好也不误红。

对威胁模型的影响是零：R 的 serverSocket(0) 能监听、system() 可用，A′ 依旧没有笼子 ⇒ 仍是 process-only / advisory、结果不可判分，probes.network=no-enforcement;serverSocket-available 明写；CDP 抓包只覆盖浏览器 target，看不到节点进程，别对外宣称零外联。三处防返工接缝一处没动：createRegistry(getMount, serverRunners) 注入实例、trusted 由 Runner 的 trust 推导、后端专有语言名在 PISTON_LANGUAGES/LOCAL_LANGUAGES —— 脚本包装全部留在 A′ 节点侧，回切官方 Docker + Piston 时前端一行不改。分叉依据仍是 13.2 / 13.4。
